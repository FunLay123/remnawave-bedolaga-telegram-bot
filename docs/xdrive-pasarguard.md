# Xdrive через PasarGuard в подписке бота

Бот остаётся источником истины биллинга, а PasarGuard — раб: он выдаёт только
xdrive-профиль (Drive/S3-транспорт, который не умеют ноды Remnawave). Клиент
получает одну ссылку подписки: бот проксирует ответ Remnawave и, если тот уже
является Xray JSON, дописывает в массив конфиг PasarGuard. Один пользователь
PasarGuard на одну подписку бота, один VLESS-UUID на все устройства.

Фоновая задача `PasarguardSyncService` — единственный писатель панели. Она
создаёт, обновляет, выключает, включает, ротирует и удаляет пользователей
PasarGuard по состоянию базы бота. Ручные правки в панели перезаписываются на
следующем проходе.

## Настройки

Все ключи читаются из окружения/`.env`. Секреты в репозиторий и логи не
попадают.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `XDRIVE_ENABLED` | `false` | Пользовательский рубильник фичи. Выключение не no-op: известные пользователи панели выключаются, создание и слияние прекращаются. |
| `PASARGUARD_API_URL` | — | Корень панели PasarGuard, например `https://panel.<домен>`. |
| `PASARGUARD_API_KEY` | — | API-ключ с правами читать, создавать, изменять, удалять и отзывать пользователей. |
| `PASARGUARD_XDRIVE_GROUP_ID` | — | Числовой id группы PasarGuard, в которой только xdrive-inbound. |
| `PASARGUARD_USERNAME_PREFIX` | `bx` | Префикс имён бота: `<префикс><id подписки>`. PasarGuard требует минимум 3 символа. |
| `PASARGUARD_INSTANCE_ID` | hostname | Метка инстанса в `note` пользователя: `xdrive-bot:<id>:sub:<n>`. |
| `PASARGUARD_SYNC_INTERVAL_SECONDS` | `300` | Интервал планового прохода, минимум 60. |
| `PASARGUARD_API_TIMEOUT_SECONDS` | `15` | Таймаут запросов проектора. |
| `PASARGUARD_SYNC_BATCH_SIZE` | `200` | Размер пачек чтения/бэкфилла. |
| `XDRIVE_CONFIG_CACHE_SECONDS` | `60` | TTL кеша xdrive-конфига на прокси подписки. |
| `XDRIVE_CLIENT_UA_REGEX` | пусто | Необязательное ограничение слияния по User-Agent; пусто — без ограничения. |

Без `PASARGUARD_API_URL`, `PASARGUARD_API_KEY` и `PASARGUARD_XDRIVE_GROUP_ID`
проектор не запускается, а слияние ничего не делает — это штатное полностью
выключенное состояние.

**Пустой `PASARGUARD_XDRIVE_GROUP_ID=` роняет старт.** Значение парсится как
целое число, и пустая строка — не «не задано». Либо не добавляйте строку
в `.env` вовсе, либо укажите число.

Слияние работает только через прокси подписки бота: домен клиентских подписок
должен быть в `SUBSCRIPTION_PROXY_HOSTS`, а `SUBSCRIPTION_PROXY_UPSTREAM` —
указывать на страницу подписок Remnawave. Провайдер слияния создаётся только
при `XDRIVE_ENABLED=true` и заданных `PASARGUARD_API_URL` и
`PASARGUARD_API_KEY`; без URL/ключа прокси не делает запросов в PasarGuard
(группа для слияния не нужна). Запрос конфига на горячем пути ограничен
коротким таймаутом в одну попытку, поэтому зависшая панель не задерживает
выдачу подписки дольше примерно 1,5 секунды; синхронный revoke — не дольше
5 секунд.

## Подготовка PasarGuard

1. Создайте inbound с транспортом `xdrive` и группу, в которой нет ничего,
   кроме этого inbound. Её id укажите в `PASARGUARD_XDRIVE_GROUP_ID`.
2. Убедитесь, что у VLESS-профиля непустое поле `encryption`. Xdrive-форк
   Xray отвергает пустой `encryption`; проверьте сгенерированный конфиг
   валидатором форка (`xray run -test` или эквивалент) до включения фичи.
3. Пользователям бота проектор всегда пишет `group_ids` ровно из одной группы
   xdrive — никакие другие inbound'ы в их подписку PasarGuard не попадают.
4. Клиентский конфиг, который отдаёт панель, содержит `xdriveSettings` с
   общими storage-кредами хоста. Бот забирает конфиг административным API по
   id пользователя и не хранит токены подписки PasarGuard.

## Подготовка Remnawave

Слияние выполняется только когда ответ Remnawave уже структурно является
Xray JSON. Клиент, умеющий xdrive, должен получать `XRAY_JSON`, а не base64:
добавьте в Remnawave правило subscription-response, которое по User-Agent
этого клиента отдаёт `XRAY_JSON`, и поставьте его **выше** системного
`Fallback Base64`. Альтернатива — выдавать такому клиенту путь `/json`.
Бот формат не навязывает: base64, Clash, sing-box, HTML и прочие тела
проходят без изменений.

## Порядок включения

1. Настройте PasarGuard и переменные окружения, оставив `XDRIVE_ENABLED=false`.
2. Запустите бота. Проектор стартует всегда, когда заданы URL, ключ и группа
   (даже при выключенном флаге), и на первом проходе только выключает уже
   известных пользователей панели.
3. Включите `XDRIVE_ENABLED=true` и перезапустите бота (или дождитесь
   прохода): бэкфилл создаст пользователей для подписок с правом на xdrive.
4. Настройте правило User-Agent в Remnawave.
5. Проверьте на тестовой подписке: ответ — Xray JSON, в нём есть профиль
   `xdrive`, клиент подключается.

Право на xdrive v1: подписка активна или триал, пользователь не заблокирован,
grace-оверлей не открыт, у тарифа ровно один положительный premium-сквад, этот
сквад входит в `connected_squads` подписки, его пул не исчерпан и не закрыт
администратором. Пробный тариф без premium-сквада xdrive не получает. Если
premium-сквад убрать из набора подписки, проектор выключает PasarGuard-пользователя
(и не считает его трафик), пока сквад не вернут: иначе xdrive обходил бы пул.

## Выключение: drain и жёсткая остановка

Выключение фичи — двухшаговая процедура, и порядок шагов обязателен.

1. **Drain.** Поставьте `XDRIVE_ENABLED=false`, но **оставьте**
   `PASARGUARD_API_URL`, `PASARGUARD_API_KEY` и `PASARGUARD_XDRIVE_GROUP_ID`.
   Перезапустите бота (или дождитесь следующего прохода). Проектор при
   выключенном флаге не создаёт новых пользователей, не сливает конфиги и
   выключает всех известных пользователей панели. Дождитесь как минимум одного
   полного прохода (`PASARGUARD_SYNC_INTERVAL_SECONDS`), проверьте в панели,
   что пользователи бота в статусе `disabled`, а подписки больше не содержат
   xdrive-профиля.
2. **Жёсткая остановка.** Только после подтверждённого drain можно очистить
   `PASARGUARD_API_*` и `PASARGUARD_XDRIVE_GROUP_ID`. Тогда проектор не
   запускается и запросов в панель нет.

Если очистить креды до drain, пользователи панели останутся включёнными с
рабочими кредами — это ошибка оператора. Пользователи при выключении не
удаляются: повторное включение флага возвращает те же UUID без переимпорта
конфигов у клиентов.

## Безопасность

- **Общие storage-креды.** Каждый выданный xdrive-конфиг содержит секреты
  `xdriveSettings` хоста, общие для всех его пользователей. Утечка конфига
  раскрывает storage-бэкенд целиком, а не только один UUID. Ротация UUID
  (`revoke_sub`) эти креды **не отзывает**: чтобы отозвать их, нужно менять
  конфигурацию хоста/хранилища (ключи, бакет, доступы). Для v1 это принятый
  риск; учитывайте его при разборе инцидентов.
- API-ключ PasarGuard задаётся только через окружение, в кабинет и клиентам не
  попадает.
- Бот не логирует тела запросов/ответов, конфиги подписок, API-ключ и
  настройки xdrive. В логах — id, имена, счётчики и статусы.

## Один инстанс на панель

Имя пользователя панели — `<PASARGUARD_USERNAME_PREFIX><id подписки>`, без
метки инстанса. Если два бота с одним префиксом смотрят в одну панель
PasarGuard, они создают/перезаписывают одних и тех же пользователей и
выключают друг друга. Панель должна принадлежать одному инстансу бота; если
это невозможно, каждому инстансу нужен свой префикс и своя группа, но общая
панель всё равно остаётся зоной повышенного риска. `note`
(`xdrive-bot:<instance>:sub:<n>`) защищает только уборку сирот: чужие записи
без маркера этого инстанса не удаляются.

## Ограничения v1

- Тариф с более чем одним положительным premium-сквадом xdrive не получает:
  непонятно, к какому пулу относить расход.
- При открытом grace-оверлее xdrive выключается; grace-трафик через xdrive не
  учитывается.
- Нет отдельных UUID на устройства: один пользователь PasarGuard на подписку.
- Расход xdrive входит в тот же premium-пул, что и premium-сквад Remnawave;
  отдельного лимита нет.
- Недоступность PasarGuard не ломает выдачу подписки: клиент получает тело
  Remnawave без xdrive, проектор повторяет запись на следующем проходе.

## Удаление подписок и интенты

Durable-интент `pasarguard_delete_intents` пишут аудированные пути удаления:
`services/subscription_deletion_service.py`, повторная регистрация
(`handlers/start.py`), обе ветки мержа аккаунтов
(`services/account_merge_service.py`), очистка дублей
(`utils/subscription_utils.py`), сброс триалов
(`database/crud/subscription.py`, `cabinet/routes/admin_users.py`), а также
админские и массовые удаления в кабинете и веб-API. После коммита эти пути
будят проектор, чтобы старый UUID PasarGuard не жил до планового прохода.

**Известное ограничение кабинетных развёртываний:** полное удаление
пользователя в кабинете (`app/cabinet/routes/admin_users.py`, удаление самого
пользователя, а не подписки) пока не пишет интент: подписки уходят каскадом
вместе с идентичностью. Уборка сирот удалит пользователя PasarGuard не позже
чем через час, но до неё он может оставаться включённым. В развёртывании
«только бот» этот путь недоступен.

## Диагностика

- Проход проектора пишет строку `Проход проектора PasarGuard` со счётчиками
  `checked/created/updated/disabled/enabled/deleted/errors`, когда что-то
  изменилось.
- Отложенный revoke виден по `subscriptions.pasarguard_revoke_pending_at`;
  отложенное удаление — по строке в `pasarguard_delete_intents`.
- Очередь удалений разбирается каждым проходом; уборка сирот — не чаще раза в
  час и трогает только пользователей с префиксом бота и note-маркером этого
  инстанса.
